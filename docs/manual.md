# Jocasta manual

The full reference for using Jocasta. For what Jocasta is and a first run, start with the [README](../README.md). Numbers in parentheses, such as (0553), are the decision records in [`docs/decisions/`](decisions/README.md) that each behaviour comes from.

## The three parts

Jocasta is a work surface around your daily omp, in three parts (0386, 0392, 0552):

- **the agent** is your own [omp](https://github.com/can1357/oh-my-pi), unforked and tuned in its `/settings`; Jocasta adds config, tools it mounts through one small extension file every pane's omp loads, and a search over past sessions (0386, 0387, 0603, 0675);
- **the work surface** is herdr, built into `jocasta` (the fork at `crates/herdr`), in its default session inside Jocasta's data folder: workspace "Jocasta" with the boss pane first and the `today` dock beside it, then one workspace per project and a worktree workspace per thread (0392, 0412, 0553);
- **the Jocasta service** runs inside herdr's server, one process (0649): bare `jocasta` launches the server, the server starts the service, and herdr's own client draws its `today` dock and its questions and takes the keys for Finish, Stop, Review, New thread and Quit (0551–0554, 0649): no plugin, pane or popup program runs for them. It keeps the thread map, reviews finished tasks through the reviewer's `review_note` findings (0394, 0678), runs the threads' checks, indexes past sessions' summaries for `history_search` (0603), and serves HTML briefs in your browser (0678). When your last terminal on it closes, Jocasta closes, asking first while threads are at work (0549).

## Prerequisites

- Windows 11 (Linux and macOS builds exist; the test suite passes there, the builds themselves are untested; see below).
- omp on PATH, signed in (`omp`, then `/login`; 0386). This build is checked against omp 19.1.1 (0535, 0623, 0663; the fork build moved the pin). Dictation is omp's own: omp downloads its speech model on first use or with `omp setup speech` (0556).
- [mise](https://mise.jdx.dev), optional: with it, setup pins gh (0476, 0542).

## Install

```powershell
irm https://raw.githubusercontent.com/zhivko-kocev/jocasta/main/scripts/install.ps1 | iex
```

Installs to `%LOCALAPPDATA%\Programs\jocasta\` (or `JOCASTA_INSTALL_DIR`; 0049): `jocasta.exe`, `config\` (the boss manual, omp, herdr and Ponytail config), `conpty\` with its notices in `THIRD-PARTY-NOTICES\` (Microsoft's ConPTY runtime, which herdr's Windows notifications and panes use; 0661) and `install.json`, and adds the folder to your user PATH. The folder is Jocasta's alone (0579): it must be empty or hold an earlier install whose `install.json` names that same folder; any other folder is refused ("jocasta install: <folder> holds files that aren't Jocasta's; choose an empty folder for JOCASTA_INSTALL_DIR."). `install.json` lists the release's top-level entries, which are what `jocasta uninstall` removes. The download's SHA-256 is checked against the hash the release workflow commits in this repository at the tag `checksums-<release tag>`, never against a file from the release, so a replaced release asset is refused (0484). The release is unpacked with Windows' own `tar` beside the install and checked before the install is touched. To upgrade, run it again: a running Jocasta keeps running, with its panes, on the old build (the companion app an older install left running stops: "jocasta install: stopping the companion app an earlier install left running."); files still in use are renamed aside as `<name>.old-<stamp>` (one in `conpty\` moves to the install's top as `conpty-<path>.old-<stamp>`, since herdr loads that folder only with exactly its own files) and the new build is copied in. Windows can't hand a running server's panes to a new build, so the installer then says "jocasta install: Jocasta is running on the old build; close it and run jocasta again to use the new one (Windows can't hand its panes over live)." (0649). omp sessions started before the upgrade run the old build until they restart.

To install a local build instead, point `JOCASTA_INSTALL_FROM` at a folder holding `jocasta-windows-x64.zip` and its `.sha256` (`mise run build` writes both to `dist\`; 0487):

```powershell
$env:JOCASTA_INSTALL_FROM = "$PWD\dist"; .\scripts\install.ps1   # from the repo, after `mise run build`
```

`scripts/install.sh` takes `JOCASTA_INSTALL_FROM` the same way, with `jocasta-<target>.tar.gz`.

## First run

```powershell
jocasta setup
```

Setup's changes are numbered migrations (0466). Each one shows its diff and is written only after `y`; it runs once per shipped version, with a marker in `~/.jocasta/agent/setup/`, so a file you edit afterwards is left alone until Jocasta ships something new for it. The first failure stops the rest and says why (exit 1). When changes are waiting, the service says so once at start, in a notification through herdr: "jocasta setup has N changes waiting: run `jocasta setup` to see them."

- Jocasta's omp snapshot over your omp files in `~/.omp/agent` (0650), one change with one `y`: `config.yml`, `keybindings.yml`, `lsp.json`, `WATCHDOG.md` and the mise skill from `config/omp/`; herdr's omp hook (`extensions/herdr-omp-agent-state.ts`, which reports each pane's state to Jocasta's herdr); and `secrets.yml` only when missing. Each file it replaces is kept first in `~/.jocasta/agent/setup/omp-backup/<UTC time>/`; a later snapshot keeps the first backup as the one uninstall puts back. Logins, sessions, memory and history are never touched;
- `~/.jocasta/agent/herdr.toml` for session `jocasta`; setup then runs `herdr config check` on it and prints what it reports, and a failed check doesn't stop setup (0401, 0440, 0466, 0554, 0608);
- the Windows Terminal scheme Tokyo Night, from Jocasta's palette (0401, 0474);
- with mise on PATH, mise's machine file `~/.config/mise/conf.d/jocasta.toml` (pinned gh; your own `config.toml` wins; 0476, 0562);
- from an install that still has the old graph (`~/.jocasta/agent/compose.yaml`), Graphiti's and FalkorDB's containers taken down when Docker runs, with one question whether their images and volume go too, and the compose file and `containers\` removed (migration 16, 0603); whatever stays is named with the one command that removes it;
- the old `jocasta` herdr plugin's folder `~/.jocasta/agent/herdr-plugin/` and its marker removed (migration 18, 0649): herdr's client draws `today` and the questions now; a herdr installed apart from Jocasta keeps the link setup made before, until `herdr plugin unlink jocasta` there;
- a note when git is older than 2.54 or missing: the question about pushes to main, master and develop needs it, and a pane's pushes there go unasked until you update git (0613);
- the calendar's secret address from `JOCASTA_CALENDAR_ICAL_SECRET` into Windows Credential Manager (0430);
- the Gmail app password (`jocasta/gmail-app-password`, or `JOCASTA_GMAIL_APP_PASSWORD`) and the Jira API token (`jocasta/jira-token`, or `JOCASTA_JIRA_TOKEN`): asked for, hidden, only when `pollers.gmail.address` or `pollers.jira.site` and `email` are set in `jocasta.yaml` and the secret isn't stored yet (0680).

To put one file back to the shipped version, run `jocasta setup --refresh herdr.toml`, or `jocasta.json` (the Terminal scheme), by name or full path: it shows the diff, asks "Refresh? [y/N]", keeps the old file as `<file>.bak.<YYYYMMDD-HHMMSS>` beside it, and reloads herdr's config after a herdr.toml refresh (0467).

After upgrading, run `jocasta setup` once: this build writes the omp snapshot and removes the `jocasta` MCP entry from the `mcp.json` files (your other entries stay; 0675). Jocasta's tools now reach omp through one extension each pane loads over a local pipe; a tool that may wait for your Allow, a check or a commit (`thread_start`, `thread_finish`, `worktree_remove`, `lesson`, `check`) says to call it with the bash tool's timeout set to 3600 s, since omp runs a mounted tool inside its bash call (default limit 5 minutes).

## Daily use

Run `jocasta` in a terminal. It starts the Jocasta service when none answers and waits for it (a hung one is ended after 15 s, herdr's session and its panes spared, and replaced; 0565, 0582), then attaches herdr's client to session `jocasta`; if the service stops while starting, `jocasta` prints its last error and "jocasta: run `jocasta diagnose` for the full log." and exits 1 (0582). The boss pane runs omp with the boss manual and continues where it was (0424), with the `today` dock beside it (boss 65 / `today` 35; 0553), drawn by herdr's client in the boss's workspace. Ask the boss for a thread in a project, press Ctrl+B then Alt+N (pick the project, write the brief), or run `jocasta thread new`; it opens a worktree workspace, plans first, and you approve the plan in its pane. Each thread runs with `--warn-cost 50` (0541) and can carry `done_when` commands its review runs (0540); it ends a task with `report_result` (0539), and its `check` runs the project's checks once per git tree (0542, 0546). When a task ends, its reviewer hands in findings through `review_note`, which keeps one only when the quoted code is in the committed file at that line (0394, 0678); `thread_finish` merges it or opens a PR (0426). The boss's `big_picture_review` answers at once ("Started acme-api's big-picture review; its result comes as an [event].") and its result reaches the boss later as one `[event]` line; one runs per project at a time (0577).

The sidebar lists the agents, Jocasta's threads; its top strip holds only `menu` (0659, 0664). Jocasta makes every workspace: herdr's own new workspace, git worktree and workspace-rename actions are gone, with their keys (Ctrl+B then Shift+N, Shift+G, Shift+W). On the boss's workspace your close workspace, new tab (the key and the tab bar's `+`), close tab, split and close pane do nothing but say "Jocasta owns this workspace: it can't be closed, split or given tabs."; other workspaces keep tabs, splits and close, so a shell beside a thread is one split away (0665). `menu` offers settings, keybinds, reload config and "quit Jocasta", the same as Ctrl+B then Alt+Q; herdr's detach (Ctrl+B then q) is gone. Help (Ctrl+B then ?) lists Jocasta's keys first (0666).

`thread_status` and `jocasta thread list` give each thread's ledger line, such as `spend $1.84 · peak context 41% (82k of 200k) · cache read 71% · 3 re-reads · 1 repeated call · 1 cache miss · 2 compactions` (0546). Requests are every assistant message and every side call omp records (`model_usage`); a cache miss is a cache write of 10,000 tokens or more after more than 5 minutes without a request on the same provider and model; compactions are omp's own, not Jocasta's `/handoff` (0582).

A review fails when the change weakens the tests: a removed test, fewer assertions in a changed test file, or an added skip or only; the reason is shown beside the Allow (0610). The reviewer also posts at most three design findings, `[P3] Design: …`, judged by `config/design-rubric.md`; they never block (0611). In a project pane, a tree with edits not yet checked runs the project's check when the agent's turn ends: a failure is given to the agent as the turn's continuation, once per tree; a check slower than the turn-end limit writes one line in `today` and reaches the agent at its next turn end (0617). Threads keep their own `check`. The weekly big-picture review runs with a $25 cost cap and, when the project's trusted mise config has a `scorecard` task, runs it first and gives the review this week's and last week's output (0608, 0616).

`today` shows, top to bottom: the date and time, `quiet` during quiet hours, a service that is down in red with its note, the weather (when `dashboard.weather` is set), CPU and memory, the quota windows (red from 80%, with the reset time when it is within a day: `5h 91% (16:30)`) and today's spend; NEEDS YOU (each row starts with its kind: `?` a question or plan, `✓` reviewed, `↗` a review request, `!` a red pipeline or a full disk; a reminder starts with its time); UNDERWAY (each thread's state, time, cost and context); LANDED TODAY; CALENDAR (a meeting that started shows `now` until it ends); MAIL, JIRA and AZURE (only once their poller is configured; one row per unread mail, open issue or failed operation, Enter opens its link; a failed round shows its one-line reason, such as `mail: sign-in refused; run jocasta setup`; this text is private (0681): the boss's `today` tool, pushes and logs carry only `mail: 3 unread`, `jira: 5 open`, `azure: 2 failed`); NEXT (your notes) and NEWS while rows are left; and its keys, `↑↓ pick · Enter go/open · f Finish · s Stop · r Review · n New` (0555, 0581), which it takes once you click it or press Ctrl+B then Alt+T; Esc, or a key it doesn't know, gives them back. Enter goes to a thread's pane or opens a row's link (such rows end in `↗`); a left click on such a row picks it and does the same as Enter on it, and a click elsewhere in the dock only gives it your keys (0660); `r` reviews the picked thread and `n` starts a new one. In a narrow dock a row keeps at least 18 columns of its title and drops context, cost and time first; the header drops the weather, then CPU and memory, before it passes two rows; the key line drops its last keys. Until the service first answers the header says "Connecting to Jocasta…"; while it doesn't answer, "Jocasta isn't answering (since 18:03); trying again…", and a key pressed then says "Not connected; try again." The service sends the dock a sign of life every 10 s; with no message for 30 s the dock and herdr's tab bar say "Jocasta isn't answering (since 18:03)" (the time of the last message) and the dock keeps its last picture dimmed, until the next message arrives (0662). A key says what it started at once ("Starting a thread in acme-api: worktree, omp, brief…"); the outcome stays a minute (0581). herdr's tab bar shows `N awaiting you · $X today` (N is NEEDS YOU's rows), drawn by Jocasta, and the time (0554, 0581). In any pane, Ctrl+B then Alt+F finishes the focused thread (merge or PR), Alt+S stops its run, Alt+R asks for a review of its commits, Alt+N starts a new thread and Alt+Q quits Jocasta (0554); Alt+1…9 switch workspaces and Alt+[ / Alt+] move between agents (0408).

The HUD round (0667–0673) adds to the dock:

- **Getting back to the boss (0667).** The boss's row is always first in the sidebar's agents list, labelled with workspace "Jocasta" and its state; click it or press Enter on it to return from a thread. Alt+1, Alt+G and Ctrl+B then w still work.
- **Thread facts (0668).** An UNDERWAY row shows, as the dock narrows and dropping from the right: the state, the last check (`✓` passed, `✗` failed), the diff against trunk (`+84` green, `−12` red), age, cost and context. A thread whose omp session file has not been written for 10 minutes shows `stuck` in red and also gets a NEEDS YOU row with `!`. A thread sent as a PR lands in LANDED TODAY with `PR #n` and its CI state (pending, passing, failing, merged or closed), read through `gh pr view` and cached (2 minutes while pending, 10 once settled, never again after merged or closed; at most about 10 PRs). The header adds `avg $x` (the mean of up to 7 prior days' spend, backfilled once at start from the last 8 days of omp session files, then kept in `<data>/spend-days.json`) and `top <thread> $x`, today's costliest thread; both give way first when the header would pass two rows.
- **The NEWS box (0668).** NEWS is a box of 5 lines, newest first across every feed. It reserves its heading and blank line (7 lines in all) before NEXT gets what is left, shrinks at small heights and goes under 3 lines. The mouse wheel over it and ↑↓ at its edges scroll it. This needs one small change in the herdr fork: the dock takes the wheel (`crates/herdr/FORK.md`).
- **Quota for every account (0669).** After CALENDAR, QUOTA has one line per logged-in account, `zi* 5h 42% · 7d 18% · resets 16:30` (a window from 80% in red; names are redacted by `omp usage --redact`, so a full email never leaves omp), then one `left 5h: 1 of 2 accounts` line per window. At small heights the `left` lines go first. There is one toast per account and window when it passes 80%, and again only after it went back under. A failing `omp usage` is quiet and the dock keeps the last good reading.
- **The check queue (0671).** While any check runs or waits the header shows `checks: <n> running · <m> waiting`. A check is let in when its recorded peak memory fits in free memory minus the reserve and its cores fit, otherwise it waits its turn; waiting does not count towards its time limit. The first run of each check, which has no record, runs alone. Records are in `<data>/checks/costs.json`; a file that can't be read counts as no records.
- **Leftovers (0670).** LEFTOVERS lists thread worktrees left on disk, one row `project/folder`, only while there are any. Pick one and press `x`: Jocasta asks "You asked to delete …" and removes it only on your Allow; the outcome shows in the dock either way. A folder that is not in the current list is ignored.
- **Scheduled threads (0673).** A project can start threads by itself. Write `<data>/projects/<pid>/schedules.yml`, a list of `{brief, days: [mon, wed], time: "09:00", done_when?: [...], heavy?: true}` (local time). Each tick starts a schedule whose latest slot is newer than its last run (or, for a new schedule, than when Jocasta first saw it, so past slots don't fire); however many slots a sleeping machine missed, it starts once. The thread opens through the Key door in plan mode, so you approve its plan; a schedule whose `done_when` the guard would ask about or deny, and one whose project already has an open thread with the same title, is skipped with a notification. A bad schedule is reported once and skipped. Editing a schedule resets it (its id is a hash of brief, days and time); state is in `schedules.state.json` beside it. The soonest 3 show in NEXT before your notes, as `Mon 09:00 acme-api: dependency bumps`.
- **Phone check-in (0672).** Set `ntfy.server` in `jocasta.yaml` to a ntfy server URL and Jocasta pushes NEEDS YOU rows and finished threads to a topic it generates (two 64-character topics in `<data>/ntfy-topics.json`, never typed); `jocasta diagnose` prints a `phone` line with the server, the mode and the main topic to the terminal only, so don't paste diagnose output with the phone on. There are three modes. Off: `ntfy.server` unset, nothing is sent. Public: the server is set and `ntfy.ownServer` is not true, or `ntfy.token` is empty; only a kind and a count leave the machine (`Jocasta: 2 need you`, `Jocasta: an Allow is waiting`), no title, project, command or path, no buttons and no reply stream, and the token is never sent. Own: `ntfy.ownServer: true` and `ntfy.token` set; pushes carry the text of the question (its message, never its detail) with Allow and Deny buttons and Jocasta subscribes to the reply topic with the token. Each token in a button is single use, good only for its own open question, and the typed Allow code still works. Trust boundary: in own mode the buttons carry the ntfy access token in their `headers.Authorization`, so the token is inside each notification and in the server's message cache; anyone who can read the topic can answer an Allow, and those are the same people who hold the token, including the server's operator. `ntfy.ownServer: true` on a server that isn't yours is your claim; the token is the only other gate. Pushes are held during quiet hours (an Allow is not), and each row is pushed once (`<data>/ntfy-sent.json`, pruned after 7 days).
- **Briefs of the day (0680).** The morning brief is built by Jocasta on the first refresh after 06:00 and when you press `b` in the dock (it also opens then); it never opens by itself. It shows today's meetings in order, what needs you, the PRs awaiting your review, the work graph (threads, waiting starts, their PRs and CI), red pipelines, your unread mail, open Jira issues and failed Azure operations, quota and the machine, and the news. Mail, Jira and Azure text is private: it shows in `today` and in this brief only, and no model, push or log reads it. The weekly brief is built when the weekly review is due and lists production and cost per project, the week's journal numbers (threads finished, gate-fail and sent-back rates, stuck and over-budget counts, median cost and time), what each check cost, leftovers and the drift review. A BRIEFS section in the dock lists both; pick one and press Enter.

Some actions wait for your Allow (0484, 0544): merging a thread or opening its PR (`thread_finish`), removing a leftover worktree (`worktree_remove`), starting a thread in a project other than the one whose pane you last focused or with a `done_when` the guard asks about (0580), saving a lesson (the question shows its full text), and from the command line `jocasta thread send|stop|finish` and `jocasta worktree remove`. The question opens over the first terminal you attached (one a pane runs never gets it), titled "Jocasta: Allow or Deny", in front of whatever you're on (0553). Allow takes the three letters it shows: type them; the arrows or Tab pick a choice, and Esc, or Enter on Deny, denies (0558). Finish's Merge and PR and the close question's Stop everything take a code the same way; Cancel stays one key (0568). The question ignores keys for its first 750 ms, so typing meant for a pane isn't spent on it; the code stays on screen and PgUp/PgDn read a long question; after a second wrong code it says "Wrong code; one try left, then it counts as Deny." (0578). Deny, a third wrong code, no answer within 2 minutes, closing its terminal, or closing Jocasta all count as Deny, and the boss is told which. One question per action and thread is open at a time: asking again brings it to the front ("Finish: already asking about acme-api/retry."), and Allow questions go before the ones your keys opened (0578). Only the boss pane can use the boss's tools: it gets a per-run key. Every omp Jocasta starts in a pane gets that pane's own key, `JOCASTA_PANE_KEY`, kept in `<data>/panes.json`; `jocasta mcp` sends it, so a tool call can't claim to come from another pane. A pane started by a build before this one gets its key when its omp starts again (0578). `history_search` answers from the pane's own project, each line quoted «…» with its source and date (0484, 0603).

A push to `main`, `master`, `develop` or the project's own trunk on a network remote asks you once per repo (0613). Every pane Jocasta starts gives git a `pre-push` hook (git 2.54 or newer) that asks the service, and Jocasta asks "Push to main in acme-api?". Allow: the repo takes pushes straight to its protected branches from now on, unasked. Deny: it takes pull requests instead, and such a push is refused with that reason. Either answer is kept in the `push:` map of `~/.jocasta/agent/projects.yaml` (`direct` or `pull-requests`), where you can change it. A feature branch, or a push to a folder remote, passes unasked. With Jocasta not running, a push to a protected branch is refused. The guard denies `git push --no-verify` and any change to the hook's git settings.

When a thread needs you, herdr shows a system notification with its request sound; a finished thread chimes with herdr's done sound (0554, 0569). Every notification is also a line in `<data>/notifications.jsonl`. On Windows, panes run on the bundled ConPTY (`conpty\`, 0661); if a pane misbehaves there, `HERDR_WINDOWS_CONPTY=system` in the environment `jocasta` starts from puts them on Windows' own.

Closing a thread or stopping everything ends every process its panes started (omp's workers, language servers, MCP servers), and a worktree is removed only once no process works in it; otherwise the reason names them (0486). A process counts as a pane's only when it started at or after its parent, so a process whose parent's pid Windows has given out again is never reached; `taskkill /T` isn't used (0573's review, SRV-A-1).

Nothing runs without Jocasta (0549): closing the terminal, quitting herdr's client or Ctrl+B then Alt+Q stops everything Jocasta started: the service, herdr session `jocasta` and every omp in it, the relay. There is no keep-running-in-the-background. With threads working or awaiting you, closing the terminal opens a new terminal on the same herdr session (Windows Terminal, else a console window) and asks there, titled "Jocasta: Stop everything?": "Stop 2 working threads and 1 awaiting you? They pick up where they left off next time."; Cancel leaves everything as it was (0563, 0581). The quit key asks the same. On the next `jocasta`, threads that were mid-turn go on with that turn (`omp --restore`) and the others reopen idle; GitHub, Azure DevOps and the calendar are read again, and reminders and events that came due meanwhile show once (0549). The service runs inside herdr's server, so one can't outlive the other. An omp that ends in an open Jocasta pane is started again there (0521). Your other herdr sessions and omp windows are never touched.

Hold Right Ctrl anywhere in Windows to talk to the boss: the service sends F9 (omp's `app.stt.toggle`) to the boss pane through herdr on press and again on release, omp transcribes on this machine with its local Parakeet model, and the text is sent when you let go (0556). Holding Space in a focused omp pane is omp's own push-to-talk. There are no spoken replies (0552).

A finished thread has a brief, `thread-<task id>`, a page the service serves on 127.0.0.1 and builds by code (0678): the thread's facts and cost, its phases as an animated flow, the checks with their durations, the reviewer's notes as cards, a map of the changed files and the diff (2,000 lines at most). The Done toast opens it; its buttons Finish (merge or PR) and Send run the same code and Allow gate as `thread_finish` and `thread_send`. The boss's `show {title, sections}` draws a brief from a spec (sections `text`, `facts`, `flow`, `map`, `diff`, `list`) and opens it; a spec with an unknown node in an edge or more than 200 nodes is the tool's error. There is no free-hand drawing: to change a diagram, ask for a new `show` (0679). Motion stops under `prefers-reduced-motion`.

## Commands

| Command | What it does |
|---|---|
| `jocasta` | opens the work surface (herdr session `jocasta`) and starts the Jocasta service |
| `jocasta setup` | shows what Jocasta adds to omp, herdr, Windows Terminal and mise; writes after `y` (0466) |
| `jocasta setup --refresh <file>` | puts `herdr.toml` or `jocasta.json` back to the shipped version after a diff and `y`, keeping a `.bak.<stamp>` copy; an unknown file exits 2 (0467) |
| `jocasta uninstall` | removes everything install and setup added (herdr session `jocasta`, setup's writes, the calendar, Gmail and Jira credentials, the `config.jocasta-*.override.toml` mise files, the PATH entry, an earlier install's app's autostart value and WebView2 data, `~/.jocasta/agent` except `private-names.txt`, and from the install folder only the entries its `install.json` lists, then the folder once it is empty) after one list and one `y`; asks separately about the data folder; puts back each omp file the snapshot replaced while it is still the snapshot's (one you changed since stays, with yours from before as `<name>.before-jocasta`); keeps your mise `config.toml` and mise itself; refuses while Jocasta is running (0468, 0579). A folder that also holds your files stays ("removed Jocasta's files from <folder>; kept the folder (it holds other files)"); an install from before the list is removed whole only when every entry is a release's name, else it is kept ("kept <folder>: it holds files that aren't Jocasta's (…); remove Jocasta's files from it by hand"). On Windows it first refuses while omp sessions run programs from the install ("jocasta: omp sessions still run programs from <folder>: jocasta.exe mcp (pid 4120), … Close them, then run jocasta uninstall again."), and the files the running `jocasta.exe` holds go once it exits. It deletes a folder only while it still holds what put it on the list, never follows links or junctions, and never touches a drive root or your home folder ("kept <path>: …"; 0484). It works the same on Linux and macOS |
| `jocasta diagnose` | writes `<data>\diagnose\` (state, the newest 400 log lines) and opens a read-only omp pane, tab "diagnose" in workspace Jocasta, to find what's wrong (0472). The state and log, with project names and folders, go to your model provider with its first message (0484) |
| `jocasta project list \| add <path> \| remove <name\|id>` | lists, adds or removes a project (0111) |
| `jocasta thread new <project> "<brief>" [--title <t>] [--done-when "<cmd>"]... ## What the guard doesn't stop

The guard is a list of command shapes that omp refuses or asks about before running (0450, 0485). It stops the usual ways of losing work or a login: force pushes, deleted remote and force-deleted local branches and refs, `reset --hard`, `clean`, discarding checkouts, dropped stashes (asked first), repo and release deletion through `gh`, recursive deletes, piping downloads into a shell, mise's trust and global changes, git aliases, and reading or printing tokens and credential files (`gh auth token`, `gh auth status -t`, `az account get-access-token`, omp's logins as `omp auth export` and its `agent.db`, gh's `hosts.yml`, SSH keys, Jocasta's `jocasta-service.json` and its old name `frontier.json`). It also catches `git.exe` and a full path to git, and PowerShell's `rm -Recurse` and `ri` forms.

Record 0580 widened it. Denied: combined force flags (`push -fu`, `-uf`, `-fv`, `-vf`, `-fq`, `-qf`), pushes to `:main` or `:master`, the git rules with the program written `GIT` or `Git` (Windows runs both as git), `restore --worktree`, `-W` and `--source`, `update-ref` on `refs/heads/`, `git credential fill` and `git credential-manager get`, omp's own critical shapes (`<(curl`, `<(wget`, `eval $(curl`, `eval $(wget`, piping into `zsh` or `fish`, `sudo rm`), `gh repo edit --visibility`, and omp's logins as `omp auth export` and its `agent.db` (with its `-wal` and `-shm` files), where omp keeps them now instead of `auth.json`. Asked about (and refused in subagents): `gh pr merge`, `gh release create`, and `npm`, `pnpm`, `bun` and `cargo` `publish`. The alias rules match `git config alias.…` and `--config-env`, so fewer harmless `git -c` commands are caught.

A thread's `done_when` commands are run by Jocasta, outside omp, so each is checked against the same rules before the thread starts, at every door (0580). A denied one refuses the start ("thread_start: done_when `<cmd>` is denied by Jocasta's guard (`<rule>`); no thread was started."). One the guard asks about makes the boss's start wait for your Allow, whose box lists each command ("It runs when the work is reviewed:  `bun test auth`"); `jocasta thread new` asks nothing, so it refuses such a command: "jocasta thread new: done_when `<cmd>` needs your Allow under Jocasta's guard, and jocasta thread new asks nothing; have the boss start it. No thread was started."

It is pattern matching, not a boundary. Every pane runs omp as you, with your logins, under omp's `yolo` mode. So the guard can't stop:

- a script the agent writes first and then runs, or an interpreter one-liner beyond the shapes listed in `config/guard.yml` (`python -c`, `node -e`, `bun -e` deletes are asked about; anything else runs);
- shell commands run through omp's `eval` tool (Python or JavaScript), which skip `bash.patterns` entirely;
- a dangerous command hidden in a way the shapes don't match (an unusual flag order, a variable holding the path, a command read from a file);
- anything that reaches your logins or other projects through a tool rather than a command.

It guards the agent's commands only: a command you run yourself in a pane with omp's `!` runs as typed, without the guard (seen in the campaign's re-test, 0481).

A thread that reads a prompt-injected README, test output or web page can therefore still do what you can do. Until thread panes run under an OS boundary (a restricted token, a separate user or a container, without your logins and with limited network; after v1, 0485), treat the guard as a seatbelt and plan approval as the real gate: read the plan before approving it, and keep client repos' own hooks and `.env` files in mind.

A thread can also drive herdr through its socket as you can: run herdr's commands and press keys in its panes (0552, 0568). It can't answer a question from there: Allow, Merge, PR and Stop everything take letters that only herdr's client shows, drawn over your terminal and never in a pane, so `pane read`, `agent read` and herdr's snapshot never hold them, and a key sent to a pane never reaches the question. Each question has one reader (0578): the first terminal you attached that doesn't run inside one of Jocasta's panes, by herdr's client id, with the process at the other end of its connection read from the OS when it attaches; an answer from any other terminal is refused ("This question is shown in another terminal.") and settles nothing, and closing the reader's terminal ends the question as its fallback (Deny, or Cancel). So a `jocasta` a thread runs in its pane attaches as a terminal but never reads a question. It doesn't stop a program a pane starts detached, outside the pane's process tree, that attaches as a terminal of its own before yours does; nor a terminal whose process the OS doesn't report, which counts as yours. Nor does it stop a program running as you from doing by other means what the choice would have done.

A brief page runs one script and one stylesheet from the service itself, with no eval and no external URL: its content-security-policy is `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`. The service refuses (403) a request whose `Host` isn't `127.0.0.1:<port>` or `localhost:<port>`, one without the page's cookie, and a `POST` whose `Origin` isn't its own or whose body isn't JSON; the page writes text only through `textContent` and opens only `http` and `https` links with `rel="noopener noreferrer"` (0678, 0681).

## `/share`

`/share` is omp's. In Jocasta's panes and the boss, `share.serverUrl` points at the local relay's port, which serves nothing but the relay's rooms, so a plain `/share` there never leaves the machine (0561). In an omp outside Jocasta it uploads the session as an encrypted blob to `my.omp.sh/s` by default; with `--gist` it makes a GitHub gist. Then the whole conversation leaves the machine, client code included (0047). Think before you run it.

## Linux and macOS

Builds exist for linux-x64 and darwin-arm64 (`scripts/install.sh`, installing to `~/.local/share/jocasta/`), with the same server and service. An upgrade on Linux hands a running Jocasta to the new build through herdr's live handoff (`jocasta server live-handoff --import-exe <new jocasta>`): its panes and their omps keep running, and the service starts again on the new build; on macOS, where the handoff's own tests haven't passed, a running Jocasta keeps the old build until you close it and run `jocasta` again (0649). `install.sh` refuses a folder that isn't Jocasta's as `install.ps1` does, unpacks beside the install (`<folder>.new-<stamp>`) and swaps it in, so no stale file stays (0579); `jocasta uninstall` removes what it put there. Right Ctrl dictation, the terminal reopened for the close question (it waits for the next `jocasta` instead), the calendar's Credential Manager entry and uninstall's check for omp sessions running from the install are Windows-only. CI runs the test suite on Ubuntu and macOS as on Windows (0572); the builds themselves haven't been run there (0481).

## Development

Requires [mise](https://mise.jdx.dev): the repo's `mise.toml` pins Rust 1.100.0 with clippy and rustfmt (0627), Bun 1.4.3, Zig 0.16.0 (for the herdr fork's terminal library; 0649), cargo-deny, cargo-machete and cargo-nextest (`mise.lock` holds their URLs and checksums; 0476). Jocasta and `jocasta-bench` are Rust (0625, 0636); the brief page's script, the docs and config checks, the install-script tests and the scorecard stay TypeScript on Bun. Under Jocasta's mise file (paranoid trust) it needs `mise trust mise.toml` once in the checkout, and again after each change to it; Jocasta's threads trust their unchanged copy themselves (0596):

```powershell
mise install --locked
mise exec -- bun install --frozen-lockfile   # the Bun checks' packages
mise run check                       # typecheck, lint, knip, the Bun tests; rustfmt, clippy, the Rust tests, cargo-deny, cargo-machete
mise run build                       # cargo build --release, then scripts/build.ts packages dist/
mise run evals                       # jocasta-bench evals (0636)
mise run smoke                       # the herdr smokes on this machine, in a throwaway session
mise exec -- cargo run --bin jocasta -- --help   # a dev run of the CLI
```

Opt-in smoke: `JOCASTA_HERDR_SMOKE=1` (a real herdr; `mise run smoke`). Live checks set `JOCASTA_HERDR_SESSION` to a throwaway session name so they never touch session `jocasta` (0441). Evals run omp on real cases: `JOCASTA_EVALS_REAL=1 mise run evals` (0375).

`mise run build` writes `dist/<target>/` for this machine's target (`jocasta.exe`, `config/`, and on Windows `conpty/` and `THIRD-PARTY-NOTICES/` from the ConPTY package `crates/herdr/packaging/windows/conpty.json` pins, downloaded once and hash-checked; 0661) plus `dist/jocasta-<target>.zip|.tar.gz` and its `.sha256` (0044), and `jocasta-bench` in `dist/<target>/bench/`, outside the archive; each release runner builds its own target. herdr is compiled into `jocasta.exe` from `crates/herdr`, with the `today` dock and the question box drawn by its client. Pushing a `v*` tag publishes a GitHub release (0051).
